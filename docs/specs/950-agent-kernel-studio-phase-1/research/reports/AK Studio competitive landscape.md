# AK Studio Leads on Building, Lags on Operating

Agent Kernel Studio Phase 1 occupies a square of the November 2026 market that no other vendor fills: a local, sign-in-free desktop studio that treats ordinary framework code in a git folder as the source of truth, spans **eight agent frameworks**, drives the developer's own coding agent with per-turn accept and revert, ties plain-language business rules to the code and tests that enforce them, and deploys through plain Terraform to **six targets across AWS, Azure and Google Cloud**. Every comparable product is single-framework (LangSmith Studio, ADK web, Mastra Studio, Foundry Toolkit), single-cloud (AgentCore, Gemini Enterprise Agent Platform, Foundry Agent Service), or a hosted canvas in retreat (**OpenAI Agent Builder shuts down on 30 November 2026**, Foundry's visual workflow designer on 1 December, and Flowise was archived in August). The market's 2026 direction, with code as the durable artifact, coding agents plus vendor skills as the authoring path, and evals as code, validates the plan's core thesis. Phase 1 falls short on everything after the first local run: it has no simulated users, eval history or experiment comparison, no span-level traces for three of its eight frameworks, and no environments, CI handoff, rollback or view of a deployed system. That is exactly where the hyperscalers invest most. Most of these operate-and-govern gaps sit in fifteen parked later-phase briefs that have no schedule yet; they were written for the hosted concept that is now the planned direction after Phase 1, together with support for multiple coding agents. A second set (user simulation, red-teaming, datasets, OpenTelemetry ingestion, local models, prompt versioning, CI generation, and the terms under which Studio may drive Claude Code) appears nowhere in the plan. Of the Phase 1 bets, six are genuine differentiators, six are table stakes, and four (the Electron form factor, laptop-applied Terraform with local state and one target, Claude Code as the only coding agent, and traces built from stream events instead of OpenTelemetry) run against where the market moved in 2026.

## Four canvas retreats in 2026 moved the market toward AK's thesis

The single most important market fact for this plan is that the vendors who made the visual canvas the source of truth spent 2026 backing away from it. OpenAI deprecated Agent Builder on 3 June 2026 and shuts it down on **30 November 2026**, together with its hosted Evals product and reusable prompt objects, telling users to move to the Agents SDK or ChatGPT Workspace Agents and to Promptfoo for evals ([OpenAI deprecations](https://developers.openai.com/api/docs/deprecations)). Its own migration guide concedes that the code export "does not convert your workflow graph or guarantee that every behavior transfers unchanged" ([OpenAI migration guide](https://developers.openai.com/api/docs/guides/agent-builder/migrate-from-agent-builder)). Microsoft retires the Foundry workflow designer on **1 December 2026** and points new builds at Agent Framework code or YAML ([Microsoft Learn: Foundry workflows](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/workflow)). AWS closed console-configured Bedrock Agents, now "Classic", to new customers on 30 July 2026 ([AWS: Bedrock Agents Classic](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-classic-maintenance-mode.md)). Flowise, a 55,000-star open-source builder owned by Workday, was archived in August after its team concluded that "the typical rigid workflow low-code approach quickly hits the limit when it comes to complexity" and that developers "are increasingly relying on new coding agents" ([Flowise discussion #6727](https://github.com/FlowiseAI/Flowise/discussions/6727)); the sunset page names Claude Code as the destination ([Flowise sunset](https://flowiseai.com/sunset)).

What replaced the canvases is the architecture AK Studio already has. AWS says "pre-built skills give coding agents current AgentCore best-practice knowledge", shipped as a Kiro Power with plugins for Claude Code, Codex and Cursor announced ([AWS ML blog](https://aws.amazon.com/blogs/machine-learning/get-to-your-first-working-agent-in-minutes-announcing-new-features-in-amazon-bedrock-agentcore/)). Microsoft's Foundry Toolkit lets GitHub Copilot create agents "often from a single prompt" using Foundry skills ([Microsoft Tech Community](https://techcommunity.microsoft.com/blog/azuredevcommunityblog/microsoft-foundry-toolkit-for-vs-code-is-now-generally-available/4511831)), and Anthropic steers Managed Agents users to Claude Code with a built-in claude-api skill ([Claude blog](https://claude.com/blog/claude-managed-agents)). Even the surviving low-code platforms added MCP endpoints so Claude Code can build and run their flows: n8n exposes an instance-level MCP server ([MindStudio](https://www.mindstudio.ai/blog/n8n-mcp-server-claude-code-workflows)) and Sim publishes one at `mcp.sim.ai` ([Sim README](https://github.com/simstudioai/sim)). AK Studio's design, six bundled skills installed into the project and a local Claude Code session that edits real files ([05-build-with-ai](../../05-build-with-ai.md)), is the same pattern with a purpose-built review surface on top. LangChain's CEO framed the squeeze bluntly: no-code workflow builders "are getting squeezed from both directions", with complex work moving to code ([LangChain blog](https://www.langchain.com/blog/not-another-workflow-builder)).

The counter-signal matters for positioning, not for the thesis. Visual automation platforms are commercially thriving: n8n's valuation doubled to **$5.2B** with an SAP strategic investment ([Highland Europe](https://www.highlandeurope.com/n8n-valuation-doubles-to-5-2bn-as-sap-makes-strategic-investment-and-plans-to-embed-the-ai-platform-into-joule-studio/)), Dify raised $30M ([VentureBeat](https://venturebeat.com/business/dify-raises-30-million-series-pre-a-to-power-enterprise-grade-agentic-workflows)) and Gumloop $50M from Benchmark ([SiliconANGLE](https://siliconangle.com/2026/03/13/gumloop-reels-50m-ai-automation-platform/)). They win on connector breadth (Sim lists 270+ integrations and 5,400+ actions) and hosted runtimes for operations teams, not on the canvas itself. AK Studio will not beat them on integrations and should not try; its buyer is the developer who would otherwise hand-write OpenAI Agents SDK, LangGraph or CrewAI code. The lesson from the retreats is also double-edged: a canvas is not a moat, so the plan's own risk register, which calls canvas-to-code "the hardest part of Phase 1" ([PHASE-1-PLAN](../../PHASE-1-PLAN.md)), describes the most expensive part of the build and the least defensible part of the value.

## No competitor occupies the local, eight-framework, three-cloud square

The November 2026 landscape breaks into five camps, and AK Studio overlaps each on one or two axes but matches none on all of them.

Pricing sources: [LangChain pricing](https://www.langchain.com/pricing), [Agno pricing](https://www.agno.com/pricing), [Mastra Platform announcement](https://mastra.ai/blog/announcing-mastra-platform).

**The canvas model is AK's clearest open position.** Products split into three models. Read-only graphs derived from code with hot reload come from LangSmith Studio, Mastra Studio, ADK web and Foundry's Agent Inspector ([LangSmith Studio docs](https://docs.langchain.com/langsmith/studio)). Canvases that are their own source of truth with one-way export include CrewAI Crew Studio, where "downloading code is a one-way export" and edited code becomes a separate automation without the visual editor ([CrewAI AMP docs](https://docs-platform.crewai.com/platform/en/guides/enable-crew-studio)), Google Agent Studio's "Get code" ([Agent Studio docs](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agent-studio/design-agents)) and the retiring OpenAI builder. Claimed two-way sync exists only over a vendor format: Inkeep relies on LLM-assisted rewriting of TypeScript ([Inkeep docs](https://docs.inkeep.com/overview)), and Salesforce's Canvas and Script views sit over its own Agent Script DSL ([Salesforce Admins blog](https://admin.salesforce.com/blog/2026/build-with-confidence-inside-the-new-agentforce-builder)). Google's ADK Visual Builder shows the failure mode AK must avoid: its edit option is "available only for agents created with Visual Builder" ([ADK Visual Builder](https://adk.dev/visual-builder/)). No reviewed product renders a canvas over mainstream framework code in a normal repository, which is precisely what AK's "the canvas is a view of the files", with only node positions kept in `.akstudio/`, promises ([04-agent-canvas](../../04-agent-canvas.md)).

**Framework neutrality and multi-cloud deploy are the second and third open positions.** Every studio is tied to one framework: LangSmith Studio targets "agents that implement the Agent Server API", and Foundry's Agent Inspector explicitly does not draw LangGraph graphs ([VS Code docs: Agent Inspector](https://code.visualstudio.com/docs/intelligentapps/agent-inspector)). Framework openness exists only at the hyperscaler runtime layer and in observability tools, never in a build-run-deploy studio. On deployment, every vendor ships to its own runtime, and several already run infrastructure-as-code from the developer's machine: the AgentCore CLI uses CDK ([aws/agentcore-cli](https://github.com/aws/agentcore-cli)), Google's Agent Starter Pack runs Terraform ([Agent Starter Pack](https://googlecloudplatform.github.io/agent-starter-pack/cli/setup_cicd)), and `azd` can generate Terraform for Foundry hosted agents ([Microsoft Learn: azd infrastructure](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/cli-infrastructure)). Terraform from a dev tool is therefore not novel; doing it across three clouds from one UI is. Thoughtworks' warning against adopting AgentCore "as a monolithic black box", with orchestration kept in portable frameworks ([Thoughtworks Radar](https://www.thoughtworks.com/radar/platforms/amazon-bedrock-agentcore)), is the buyer instinct AK's positioning should answer.

**Against the hyperscalers, Studio looks weaker than the runtime underneath it.** AgentCore alone shipped Policy, Identity with on-behalf-of exchange, an Agent Registry, gateway rate limits and A/B traffic splitting during 2026 ([AgentCore release notes](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/release-notes.html)). Agent Kernel's runtime has real enterprise depth of its own, including a queue pipeline over five brokers, a Helm chart with KEDA autoscaling and air-gap support, and identity providers for any OIDC issuer, Cognito, Entra and Firebase ([AK README](../../../../../README.md)). None of that is surfaced in Phase 1, so a buyer comparing studios will see AK as a build tool with no operate story even where the runtime would hold its own.

**Local-first is a real but cheap-to-copy advantage.** LangSmith Studio serves its front end from smith.langchain.com and redirects local users to a login ([LangChain support](https://support.langchain.com/articles/5972390316-why-am-i-being-redirected-to-the-login-page-when-using-langgraph-studio-in-dev-mode)); Google Agent Studio stores agent configs in `us-west1`, so organisations that restrict that region may be unable to create agents ([Agent Studio docs](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agent-studio/design-agents)); Claude Managed Agents is not ZDR-eligible unless self-hosted ([Managed Agents overview](https://platform.claude.com/docs/en/managed-agents/overview)). AK's principles (no sign-in, credentials stay in the existing cloud profile, every command visible, nothing depends on the app) answer each of these ([PHASE-1-PLAN](../../PHASE-1-PLAN.md)). The flip side is price: every local dev UI and vendor CLI is free (AWS charges nothing for the AgentCore CLI, harness or skills, per the [AWS ML blog](https://aws.amazon.com/blogs/machine-learning/get-to-your-first-working-agent-in-minutes-announcing-new-features-in-amazon-bedrock-agentcore/)), so a local AK Studio must be free too, and no Studio document states its licence or business model.

### The differentiators are real, and the rules layer is the most novel

The business-rules layer is the only Phase 1 feature with no close analogue. Rule cards carry a plain-language rule, "Enforced by" chips naming files and config keys, a test count, and a state recomputed "whenever a linked file changes on disk" ([06-agentic-development](../../06-agentic-development.md)). The nearest neighbours each hold part of it. Kiro extracts properties from EARS requirements and keeps "a clear, traceable link between your requirements and the tests that validate them" ([Kiro docs: Correctness](https://kiro.dev/docs/specs/correctness/)). A Tessl registry package, spec-as-source, links each requirement to owned files and `[@test]` paths, with a manifest and a semantic drift spot-check, but has no UI ([spec-verify SKILL.md](https://tessl.io/registry/spec-driven-devlopment/spec-as-source/files/skills/spec-verify/SKILL.md)). Sierra Ghostwriter takes guardrails in natural language and runs tests on every build ([Sierra](https://sierra.ai/product/ghostwriter)). AgentCore Policy compiles natural language to Cedar, scoped to tool access ([AWS What's New](https://aws.amazon.com/about-aws/whats-new/2026/03/policy-amazon-bedrock-agentcore-generally-available)). The CX platforms follow a different architecture in which the rule is the program, so drift is minimised by construction: Agentforce turns "always", "before" and "never" into deterministic logic ([Salesforce guide](https://www.salesforce.com/eu/agentforce/resources/reliable-ai-agents-guide/)). AK's separate rule registry is justified precisely because it runs eight frameworks whose enforcement mechanisms differ, so a framework-neutral layer linked to guardrails, tools, config and tests is the portable one. The mechanism itself is not proprietary (spec-as-source proves it can be built from files and skills), so the defensible part is the UI and the agent-runtime awareness, and the gap could narrow if Kiro or Spec Kit add standing rules with drift states.

There is a tension inside this differentiator. The rules view exists so that "a business owner and a developer look at the same project from three angles" ([06-agentic-development](../../06-agentic-development.md)), yet Phase 1's target user is one person at one computer, with the business owner sitting beside them ([00-project-brief](../../00-project-brief.md)), and project sharing is parked under "Teams and hosting". Every competitor that courts business owners with natural-language rules (Sierra, Agentforce, Copilot Studio, Decagon) does so through a hosted, shareable surface. In Phase 1 the rules reach a business owner only physically, or as files in git that the owner cannot open without the app.

The accept-and-revert flow is the second strong differentiator because review has become the bottleneck of AI-built agents. A practitioner post on n8n's Claude Code integration is titled "the hard part is reviewing them" ([Medium](https://medium.com/@creativeaininja/claude-can-now-build-n8n-workflows-the-hard-part-is-reviewing-them-0355bee76eb5)), and a July 2026 request against Claude Code Desktop notes that its diff viewer is read-only, with no per-file Keep or Undo ([Claude Code issue 73501](https://claudeissues.com/issue/73501-add-post-apply-diff-review-ui-keep-undo-per-file-like-github-copilot-chat)). AK's magenta pending nodes, "3 changes pending" card, git-checkpoint revert and locked "never apply or destroy Terraform" permission ([05-build-with-ai](../../05-build-with-ai.md); [09-app-settings](../../09-app-settings.md)) make the canvas a review surface, which is the one canvas role the 2026 evidence still rewards. The deploy safety UX is similarly strong: a parsed plan summary, a modal naming the account and region with a required "I have reviewed the plan" checkbox, and a destroy that requires typing the project name ([08-builder-deploy](../../08-builder-deploy.md)) go beyond the vendor deploy CLIs reviewed, none of which documents a resource-level plan step before applying.

### Four bets cut against the 2026 grain

**The Electron form factor runs against the agent-studio trend but with the coding-agent-shell trend.** LangChain replaced its Mac-only LangGraph Studio desktop app with a CLI-served web UI, its CEO celebrating "no more Mac-only, no more docker, no more desktop app!" ([X post](https://x.com/hwchase17/status/1881770525065990517)), and Letta's desktop app "was deprecated on October 12, 2026 and no longer runs" ([Letta docs](https://docs.letta.com/platform/desktop-app)). The prevailing pattern is `langgraph dev`, `adk web`, `mastra dev` or `agentcore dev` serving a browser UI on localhost, which already lets a tool own local processes without a desktop shell. The steelman is that coding-agent workspaces (Conductor, Crystal as Electron, opcode on Tauri) are desktop apps ([Superset comparison](https://superset.sh/compare/conductor-vs-crystal)), and the agent-builder desktop apps that survive are partial: Langflow Desktop has no Linux build ([Langflow download](https://langflow.org/download)) and Sim Desktop is macOS-only and connects to a server rather than running locally ([Sim Desktop docs](https://docs.sim.ai/desktop)). AK would be the only cross-platform agent-builder desktop app including Linux. The bet pays off only if the desktop delivers what a localhost tab cannot, and it carries costs (signing on two platforms, updates) the plan only partly prices in.

**The deploy model is a laptop-apply tool in a market that has moved production behind pipelines.** Agent Starter Pack stores Terraform state in a GCS bucket by default, with `--local-state` as the opt-out, and generates a CI pipeline that deploys to staging and then production ([Agent Starter Pack](https://googlecloudplatform.github.io/agent-starter-pack/cli/setup_cicd); [adk.dev](https://adk.dev/deploy/agent-engine/asp)). AgentCore projects define multiple account and region targets in `aws-targets.json` ([aws/agentcore-cli](https://github.com/aws/agentcore-cli)), and LangSmith keeps a revision table per deployment ([LangChain docs](https://docs.langchain.com/langsmith/deployment-revisions)). Practitioner write-ups say production applies "should not come from a developer's laptop" ([freeCodeCamp](https://www.freecodecamp.org/news/how-enterprise-teams-manage-infrastructure-at-scale-with-terraform)). Phase 1 inverts each default: local state with a warning, one target per project, redeploy without rollback, and CI as an explicit non-goal ([PHASE-1-PLAN](../../PHASE-1-PLAN.md)). There is also an unaddressed secrets consequence. The plan carefully keeps model keys out of `terraform.tfvars` by passing them at run time ([08-builder-deploy](../../08-builder-deploy.md)), but Terraform "stores your state in a plaintext file, which includes any secret values you defined in your configuration" ([HashiCorp](https://developer.hashicorp.com/terraform/language/state/sensitive-data)), so with the local-state default those keys still land in `deploy/` on the developer's disk.

**Claude Code exclusivity is the riskiest single dependency.** Competing desktop shells support at least Claude Code plus Codex, and the Agent Client Protocol registry lists roughly 25 to 50 agents ([Morph: ACP](https://www.morphllm.com/agent-client-protocol)), with Thoughtworks placing ACP at "Assess" ([Thoughtworks Radar: ACP](https://www.thoughtworks.com/radar/platforms/agent-client-protocol-acp)). Anthropic's standing rule is that third parties may not "offer claude.ai login or rate limits for their products" ([Claude Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)), and it tightened enforcement three times in 2026: consumer OAuth tokens in third-party tools were declared a terms violation in February ([The Register](https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access)), third-party harnesses lost subscription limits in April ([Hongkiat](https://www.hongkiat.com/blog/anthropic-closed-openclaw-loophole/)), and programmatic use, including the Agent SDK and headless mode, moved into a separate usage pool in May ([The Register](https://www.theregister.com/ai-ml/2026/05/14/anthropic-tosses-agents-into-the-api-billing-pool/5240748)). No primary Anthropic page rules on the exact case of a desktop app launching the user's own signed-in CLI, which is why the plan needs to state its position. The Phase 1 disconnected state simply tells the user to "install and sign in" ([05-build-with-ai](../../05-build-with-ai.md)), without stating which authentication mode Studio expects. The content side of multi-agent support is already done, because AK's skill installer targets Copilot, Claude, Cursor, Windsurf, Codex and Aider ([skills.py](../../../../../ak-py/src/agentkernel/skills/skills.py)); the exposure is in the process bridge.

**Building the trace from stream events departs from where tracing converged.** The plan accepts that "frameworks that do not stream give run-level timing only" ([07-builder-test-and-trace](../../07-builder-test-and-trace.md)), which by the wizard's own capability chips means CrewAI, Smolagents and the Claude Agent SDK ([03-new-project](../../03-new-project.md)). Foundry Toolkit runs a local OTLP collector beside its live event view ([VS Code docs: tracing](https://code.visualstudio.com/docs/intelligentapps/tracing)), and AgentCore's Agent Inspector writes OpenTelemetry spans to local JSONL ([Classmethod](https://dev.classmethod.jp/en/articles/agentcore-cli-inspector-web-ui/)). The OpenTelemetry GenAI conventions are still entirely at "Development" status, and the OpenAI Agents SDK does not emit them natively ([John Hodge](https://john-hodge.com/blog/opentelemetry-genai-semantic-conventions/)), so a pure OTel approach would not be clean either. A hybrid of stream events for live display and a local OTLP receiver for span detail would close the gap, and the AK runtime already exports through OpenLLMetry and Logfire.

## Testing clears the local floor but stops short of the 2026 evaluation loop

On the local inner loop, Phase 1 is at parity. The design starts the project with `uv run python app.py`, chats over "the same REST and SSE interface a deployed project exposes", draws a span tree with run, hook, guardrail, runner, LLM, tool and handoff spans, shows **run-level token and cost chips and per-span tokens, latency and cost**, resolves paused tool calls with Approve and Deny, and on failing tests shows Prompt, Expected, Actual and a score (0.62 in the design) with "Replay in Test" and "Fix with AI" ([07-builder-test-and-trace](../../07-builder-test-and-trace.md)). That matches LangSmith Studio, ADK web, Mastra Studio and Foundry's Agent Inspector, whose Tokens tab and MCP approval buttons set the same bar ([VS Code docs: Agent Inspector](https://code.visualstudio.com/docs/intelligentapps/agent-inspector)). One design detail needs a decision: the stream event types the trace is built from (message, text delta, reasoning, tool call and step events) include no usage event, so the per-span token and cost figures on the artboards have no stated data source.

The late-2026 evaluation bar is a loop, not a test runner. AgentCore Evaluations reached GA on 31 March 2026 with **13 built-in evaluators**, online sampling of live traces and on-demand runs for CI regression ([AWS What's New](https://aws.amazon.com/about-aws/whats-new/2026/03/agentcore-evaluations-generally-available)), then added user simulation, batch evaluation, trace-driven prompt recommendations and A/B testing by June ([AgentCore release notes](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/release-notes.html)). Google added Agent Simulation with synthetic users and an Agent Optimizer that clusters real failures ([Google Cloud Next '26 wrap-up](https://cloud.google.com/blog/topics/google-cloud-next/google-cloud-next-2026-wrap-up)). ADK lets a scenario be a starting prompt plus a goal-driven conversation plan run by an LLM simulator ([Google Developers Blog](https://developers.googleblog.com/announcing-user-simulation-in-adk-evaluation/)), Mastra Studio compares 2 to 10 experiment runs against a baseline over versioned datasets ([Mastra Studio docs](https://mastra.ai/docs/studio/overview)), and Braintrust classifies each row as improvement, regression, tradeoff or tie ([Braintrust docs](https://www.braintrust.dev/docs/guides/experiments/run)). Adoption is already broad: in LangChain's late-2025 survey **52.4% of teams ran offline evals and 37.3% online evals**, while 29.5% did not evaluate at all ([LangChain: State of Agent Engineering](https://www.langchain.com/state-of-agent-engineering)).

Against that loop, Phase 1 meets two steps and misses four. It meets "save a session as a test case" directly and "run the suite in CI" indirectly, because AK tests are plain pytest that run outside the app. It has no run history or side-by-side experiment view (the only compare mode is a trace-versus-trace view marked second pass and not drawn), no simulated users anywhere in the plan or the parked briefs, no dataset management, and no online evaluation. The underlying choice is sound: putting DeepEval and Opik judges inside pytest in the repo matches Foundry's evals in VS Code Test Explorer and OpenAI's own redirect from a hosted Evals UI to the open-source Promptfoo, which it agreed to acquire in March 2026 ([OpenAI](https://openai.com/blog/openai-to-acquire-promptfoo)). "Evals as code, Studio as the viewer" is a defensible stance; the viewer just needs history and comparison to meet the bar.

Above the floor, the debugging and model tooling that developers now expect is absent from every Studio document. LangGraph Studio's time travel lets a developer edit a node's output and fork the run ([LangChain docs](https://docs.langchain.com/langsmith/human-in-the-loop-time-travel)), which is LangGraph-specific and defensibly omitted from a framework-neutral tool. The rest is not framework-specific: Foundry Toolkit offers breakpoints and step-through in agent code ([VS Code docs: Agent Inspector](https://code.visualstudio.com/docs/intelligentapps/agent-inspector)) plus local models through Ollama and Foundry Local ([VS Code docs: Foundry Toolkit](https://code.visualstudio.com/docs/intelligentapps/overview)), Phoenix replays a stored LLM span in a prompt playground with side-by-side model comparison ([Phoenix docs](https://arize.com/docs/phoenix/prompt-engineering/overview-prompts/span-replay)), and Langfuse versions prompts with movable environment labels for instant rollback ([Langfuse docs](https://langfuse.com/docs/prompt-management/features/prompt-version-control)). Safety testing has also become mainstream: Microsoft's ASSERT "generates adversarial tests from policies" ([Foundry Build 2026](https://devblogs.microsoft.com/foundry/agent-service-build2026/)). AK's fixture already contains a rule, BR-007 "Jailbreak attempts are blocked", enforced by an input guardrail ([00-project-brief](../../00-project-brief.md)), so generating adversarial cases from business rules is a natural extension that nobody has scoped.

Interoperability is surfaced only at the configuration level. The Protocol tile maps REST, WebSocket, MCP, A2A and AG-UI onto `config.yaml` blocks ([04-agent-canvas](../../04-agent-canvas.md)), but consuming external MCP servers is a parked L10 design, and the local test speaks only REST and SSE. AG-UI reached 1.0 with integrations listed for most of AK's frameworks ([AG-UI docs](https://docs.ag-ui.com/introduction); [CopilotKit](https://www.copilotkit.ai/blog/ag-ui-1.0)), and AgentCore's CLI scaffolds runtimes by `--protocol` (HTTP, MCP, A2A, AG-UI) ([aws/agentcore-cli](https://github.com/aws/agentcore-cli)). A Test column that also speaks AG-UI would get tool-call, state and interrupt events in a standard shape for the frameworks that have adapters.

The team has clearly thought through hosted-studio parity, but none of it is committed. The excluded-without-a-home category is small but strategically loaded: CI integration is ruled out of Phase 1 ([PHASE-1-PLAN](../../PHASE-1-PLAN.md)) and appears in none of the later themes, even though generated pipelines are how Google and Microsoft move developers from laptop deploys to production.

The not-considered set clusters in three places. The first is evaluation depth (simulation, datasets, online evals, red-teaming), where the parked L18 is narrower than the market. The second is developer ergonomics around models and debugging (OTel ingestion, span replay, model comparison, local models, prompt versioning). The third, and most consequential, is the risk surface of the Phase 1 bets themselves: the auth terms for driving Claude Code, an agent-neutral bridge, secrets in local state, and Studio's own licence, update and telemetry policy. Local-first users scrutinise a desktop app's network behaviour (one Letta forum thread asks why Letta Desktop was "requiring (and reaching out to) internet access" ([Letta forum](https://forum.letta.com/t/letta-desktop-requiring-and-reaching-out-to-internet-access/60))), so an unstated telemetry stance undercuts the local-only principle.

A final class of gaps sits between Studio and the runtime. Phase 1 reaches identity providers, A2UI, the Kafka, Pub/Sub and Azure Service Bus transports, LiteLLM and fault-tolerance settings only through Config forms generated from AKConfig or through the coding agent, with no brief designing for them. The runtime's identity docs themselves say "nothing enforces `roles` yet" ([identity-and-access](../../../../../docs/docs/advanced/identity-and-access.md)), so the absence of authorization UI is partly a runtime gap too. The open decisions the plan does record (whether to smoke-test the deployed endpoint, the rule file format and the Code tab's edit depth) are small next to these.

## The post-Phase-1 roadmap changes what Phase 1 must protect

The owner plans a cloud SaaS and support for multiple coding agents after Phase 1. That moves several items above from "gap" to "planned", and it turns some Phase 1 choices into decisions about how cheap the next step will be.

- **Multiple coding agents.** Build the Build with AI drawer against an agent-neutral seam now (session, prompt, streamed events, permission request, diff, checkpoint and revert, roughly the shape of ACP), with Claude Code as the only adapter in Phase 1. Adding Codex or Gemini CLI later is then a new adapter, not a rewrite of the drawer, the approval cards or the revert logic.
- **Desktop to SaaS.** The Electron choice becomes a staging decision. Keep the React renderer browser-capable and make the typed bridge to the main-process services transport-agnostic (IPC now, HTTP or WebSocket later), so the same UI can run against hosted services. This is the LangGraph Studio path from desktop app to served web UI, taken on purpose instead of as a retreat.
- **Coding-agent terms in a hosted product.** A SaaS that runs coding agents server-side on a user's behalf falls squarely under Anthropic's third-party rules (API keys or commercial terms, no claude.ai subscription login). Settle the authentication and billing model before the SaaS design, and state the local Phase 1 position now.
- **What must migrate.** `.akstudio/` (rules, saved scenarios, deploy history), Terraform state and secrets are the data a hosted service will need. Choose formats a server can read from the repository, offer a remote state backend from the start, and reference secrets by name through Agent Kernel's secret providers rather than only through `.env`.
- **Local-first after SaaS.** Once hosted, Studio competes head-on with LangSmith, CrewAI AMP, Mastra Platform and AgentCore on the operate-and-govern features in the parked briefs. Keeping the local app as the free or open-source entry point preserves the differentiator, provided the hosted product keeps files in git as the source of truth.
- **The business-owner tension resolves in SaaS.** The rules view gets the shareable surface it lacks in Phase 1; Phase 1 only needs the rule format to be stable.

## Conclusion

AK Studio's moat is the combination of real framework code, eight frameworks, three clouds, reviewed AI edits and drift-tracked rules, and the 2026 retreat from proprietary canvases makes that combination more valuable, not less. Vendor churn is now a buying criterion: OpenAI's builder lived about fourteen months, Foundry's designer ends the day after it, and AWS deprecated its own Python AgentCore starter toolkit within a year ([AWS docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/getting-started-starter-toolkit.html)). A studio that writes plain pytest and plain Terraform into the user's repository is insurance against that churn, and Phase 1 should say so explicitly. But the combination has a single point of failure the plan does not examine: canvas edits beyond config, business rules and accept-and-revert all route through Claude Code, whose third-party terms were tightened three times this year. Stating the authentication model and putting an ACP-shaped bridge behind the coding-agent drawer would protect the differentiators at little cost.

The larger strategic tension is that Phase 1 is a build-and-ship tool in a market that monetises operate-and-govern, and the runtime's strongest enterprise features are invisible in it. A handful of additions would lift Phase 1 to the late-2026 bar without breaking its local-first principle: a local OTLP receiver so every framework gets span-level traces, judge reasons plus a locally kept run history for comparison, a goal-plus-prompt simulated-user scenario, a generated CI workflow and remote-backend default for any non-dev target, MCP servers and approvals routed into the existing approval cards, and a stated no-telemetry policy. The rules layer also needs a path off the laptop, such as a CI check that fails on broken rule links (the spec-as-source precedent). Without one, the feature designed for business owners stays on a single developer's screen, where the hosted competitors courting those same owners will never be.
