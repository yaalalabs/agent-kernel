# AI-assisted agent building and business-rules/spec-driven agent development (state as of November 2026)

Scope note: research run on 2026-11-16. Many sources are vendor pages or third-party blogs; each finding is marked "(vendor)" when the source is the product's own marketing, "(primary docs)" for official documentation, and "(third-party)" for press, blogs, aggregators or competitor comparison pages. Items dated 2025 are flagged "(possibly outdated)". Several search-tool summaries returned conflicting dates; conflicts are called out inline.

## Q1. Which products let a coding agent or copilot build agents, which embed an external coding agent (Claude Code, Codex, Gemini CLI, Cursor), and what UI patterns exist for approvals, diffs, checkpoints and revert?

### Takeaway
"Describe it and the AI builds the agent" is now table stakes across hosted agent platforms (Copilot Studio, Agentforce Vibes, Sierra Ghostwriter, LangSmith Agent Builder, n8n, CrewAI Studio, Google ADK Visual Builder, Decagon AOP Copilot), but almost all are SaaS, platform-locked and generate the vendor's own artifact (Agent Script, Journeys, YAML, workflow JSON). Products that orchestrate an external local coding agent (Conductor, Crystal/Nimbalyst, opcode, Augment Intent, Zed/JetBrains via ACP) are coding workspaces, not agent-building tools; none found combines "drive Claude Code" with an agent-specific visual canvas over a framework-agnostic runtime, which is AK Studio's gap to fill.

### Inferences
- AI-assisted agent building is crowded, but the crowd is SaaS and lock-in shaped: each tool edits its own proprietary artifact (Agent Script, Journeys, Copilot Studio agents, n8n workflows, ADK YAML). An open-source, local, framework-agnostic "AI builds real Python code plus config in your repo" tool is a less crowded niche.
- The dominant review pattern on hosted platforms is "draft, preview/simulate, test automatically, then publish" (Sierra, Copilot Studio, Agentforce Testing Center). AK Studio's per-change accept/revert with canvas highlighting is closer to IDE patterns (Copilot Chat Keep/Undo, opcode timelines) and could be a visible differentiator, especially because users report Claude Code Desktop lacks per-file Keep/Undo.
- OpenAI retiring its visual Agent Builder in favor of natural-language Workspace Agents suggests the canvas alone is not a moat; the canvas needs to be the review surface for AI-made changes, which is how AK Studio frames it.
- The closest form-factor analogues to "Build with AI" are Conductor, Crystal/Nimbalyst, opcode and Augment Intent (desktop shells over local coding agents with worktree isolation), but none of them understands agent topology (agents, tools, guardrails, channels) the way an AK canvas would.

- Vellum's current product status is contradictory across sources.

## Q2. Is supporting only Claude Code a strategic risk? What multi-agent coding interfaces have become common in 2026 (ACP, AGENTS.md, skills)?

### Takeaway
Yes, moderately high. There are two separate risks: (1) a policy and billing risk, because Anthropic in 2026 restricted third-party products from using claude.ai subscription logins and moved programmatic or Agent SDK usage into a separate metered pool; (2) a market-expectation risk, because ACP (Zed, JetBrains, registry, about 25 to 50 agents), AGENTS.md and the SKILL.md format made multi-agent support cheap and expected. Comparable desktop shells (Conductor, Crystal, Zed, Intent) all support at least Claude Code plus Codex.

### Cited Findings

Use the API key authentication methods..." (primary docs). [Claude Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

### Inferences
- AK Studio driving "a locally installed Claude Code" sits close to the line Anthropic drew: if AK Studio spawns the user's own logged-in Claude Code, users may be on subscription auth inside a third-party product; if it uses the Agent SDK, Anthropic expects API-key auth and the usage lands in the programmatic pool. The spec should state the auth model explicitly and probably default to user-provided API keys or the user's own interactive CLI session, and get the branding right ("Powered by Claude", not "Claude Code" as a product label, if built on the SDK).
- ACP is the cheapest hedge: Claude is already reachable through ACP via `claude-agent-acp`, so an ACP client layer in AK Studio would keep Claude as the default while making Codex, Gemini CLI, Copilot, Junie and Kiro pluggable later. Note that the Claude ACP adapter still sits on the Agent SDK, so the Anthropic auth policy applies either way.
- AK's bundled skills are already in the portable SKILL.md format and AK uses AGENTS.md, so the content side of multi-agent support is largely done; the risk is concentrated in the process-driving and permission-surfacing layer.
- Phase 1 being Claude-only is defensible as scoping (Claude Code has the richest permission/hooks/SDK surface), but competitors' baseline of "Claude Code plus Codex" means the multi-agent story should be on the roadmap and the abstraction should not hard-code Claude Code's event shapes.

- ACP agent/client counts are from secondary sources at different dates; the ACP registry itself was not fetched.
- Did not verify whether Cursor ships an official ACP agent in 2026.

## Q3. Spec-driven and rules-driven development (Kiro, GitHub Spec Kit, Tessl, others): how do they link requirements to code and tests, and detect drift?

### Takeaway
Spec-driven development (SDD) is mainstream in 2026 and crowded, but most tools link requirements to tasks rather than to enforcing code and tests. Kiro (EARS requirements to property-based tests with a traceable link) and a Tessl registry package called "spec-as-source" (requirement-level `[@test]` links, `targets:` file ownership, a manifest and a drift spot-check) are the closest to "requirement linked to enforcing code and tests, with sync checks". Drift detection otherwise lives in small open-source tools.

### Cited Findings
- Kiro specs generate `requirements.md` (or `bugfix.md`), `design.md` and `tasks.md`; variants include Feature Specs (Requirements-First and Design-First), Bugfix Specs and Quick Spec (no approval gates); "Analyze Requirements" flags inconsistencies, ambiguities and gaps before design; tasks run individually or in dependency "waves"; "Correctness" (property-based testing) is IDE-only; "Markdown Review" allows commenting on spec passages (primary docs, page updated November 12, 2026). [Kiro docs: Specs](https://kiro.dev/docs/specs/)
- Kiro property-based testing extracts properties from EARS-format requirements, decides which are testable and generates hundreds or thousands of random test cases; docs say it "maintains a clear, traceable link between your requirements and the tests that validate them"; on failure it surfaces the scenario and can update the implementation or offer to fix the Spec, implementation or the PBT itself; not every requirement maps to a property (primary docs and GA blog). [Kiro docs: Correctness](https://kiro.dev/docs/specs/correctness/); [Kiro GA blog](https://kiro.dev/blog/general-availability/)
- A generated Kiro task file maps properties to requirements, tests and implementation tasks (AWS community post). [AWS Builder Center](https://builder.aws.com/content/3J3xvomwP3iF4K7U0mFkYLyRTF5/kiro-doesnt-just-write-tests-it-proves-properties)
- Kiro steering files in `.kiro/steering/` hold persistent product, tech-stack and structure conventions, described as the main guard against drift; hooks are event-driven automations such as running checks on file save (third-party). [CodeMySpec: Kiro specs explained](https://codemyspec.com/blog/kiro-specs-explained); [skills-hub.ai](https://skills-hub.ai/blog/amazon-kiro-spec-driven-ide-2026)
- Kiro is positioned as successor to Amazon Q Developer for IDE assistance, with Q Developer sign-up closure effective May 15, 2026 (third-party). [DZone](https://dzone.com/articles/kiro-feature-to-requirements-design-tasks)
- GitHub Spec Kit (MIT): recommended flow constitution, specify, clarify, plan, tasks, analyze, implement; `/speckit.analyze` checks that artifacts agree with each other (cross-artifact consistency, not code-vs-spec drift); commands namespaced `/speckit.*` and exposed as `$speckit-*` skills in Codex (third-party guides). [Augment: Spec Kit guide](https://www.augmentcode.com/guides/github-spec-kit-practical-guide-sdd-workflow); [CodeMySpec: Spec Kit guide](https://codemyspec.com/blog/github-spec-kit-guide)
- Spec Kit passed 140K GitHub stars (third-party); release version conflicts between sources (v0.8.9 in May 2026, 0.10.x in June 2026, v1.0.6 in September 2026). [BuildMVPFast](https://www.buildmvpfast.com/blog/github-spec-kit-140k-stars-spec-driven-coding-hands-on-2026); [Spec Kit history](https://github.github.com/spec-kit/history.html)
- Tessl launched a Spec Registry (open beta, 10,000+ library specs) and the Tessl Framework (closed beta) in 2025 (vendor, possibly outdated). [Tessl launch blog](https://tessl.io/blog/tessl-launches-spec-driven-framework-and-registry/). ### Inferences
- The SDD crowd (Kiro, Spec Kit, Tessl, OpenSpec, Intent) targets developers and whole features; the unit is a feature spec, not a standing business rule. AK Studio's unit (an always-on business rule with state) is closer to compliance/traceability than to SDD.
- The spec-as-source package shows the mechanics AK Studio needs (rule to owned files to tests, manifest, link checks, CI regeneration, semantic drift check) can be built with plain files plus skills; this validates the `.akstudio/` file-based design but also shows the mechanism is not proprietary. The differentiator has to be the UI (state badges, coverage, Fix with AI) and agent-runtime awareness (guardrails, tools, config).
- Kiro's PBT "fix the spec, the implementation, or the test" choice on failure is a good precedent for AK Studio's "Fix with AI" on out-of-sync rules: offering which side to change is better than always changing code.
- Drift detection via hashing or git diff against declared file mappings is the common cheap approach; semantic drift (does the code still enforce the rule) requires an LLM pass or tests, which is where test linkage matters.

## Q4. Business-rule and policy authoring for conversational agents (Parlant, Agentforce, Decagon, Sierra, Rasa CALM, Google CX Agent Studio, AgentCore Policy, Copilot Studio): how do they express, enforce, test, and show compliance or drift?

### Takeaway
Every major conversational-agent platform now lets rules be written in natural language, but they converge on one design: the plain-language rule is itself (or compiles into) the executable artifact, enforced by the runtime (Parlant guideline matching, Agentforce Agent Script, Decagon AOPs, Sierra Journeys, Rasa flows, AgentCore NL-to-Cedar). Testing is a separate surface (simulations, Testing Center), and none found shows a per-rule "linked code and tests, coverage, out of sync" view.

### Cited Findings

**Parlant (open source)**
- Guidelines are natural-language condition/action rules; the engine selects relevant guidelines per turn, enforces matched ones and logs how the agent interpreted the situation; journeys are multi-step flows with state, branching and backtracking, and guidelines can be scoped to a journey (primary docs). [Parlant: Agentic design](https://parlant.io/docs/production/agentic-design); [Parlant: Journeys](https://parlant.io/docs/engine-internals/journeys)
- Explainability: Attentive Reasoning Queries (ARQs) drive guideline matching, with logs recording each guideline's ID and condition; debugging exposes the applied-guideline IDs on agent state and a hook recording each match's ID, score and rationale (primary docs). [Parlant: Explainability](https://parlant.io/docs/advanced/explainability); [Parlant: Debugging](https://parlant.io/docs/engine-internals/debugging)
- Parlant docs concede LLMs cannot be fully constrained and recommend a layered approach (primary docs). [Parlant: Agentic design](https://parlant.io/docs/production/agentic-design)

**Salesforce Agentforce**
- Agent Script is the language behind the new Agentforce Builder, with Canvas and Script views and "doesn't require coding skills" (vendor). [Salesforce Admins blog](https://admin.salesforce.com/blog/2026/build-with-confidence-inside-the-new-agentforce-builder)

[Salesforce Architects: Hybrid reasoning](https://architect.salesforce.com/docs/architect/fundamentals/guide/hybrid-reasoning-agentforce-builder-agent-script)

- From the week of July 13, 2026 new agents can only be created in the new builder; legacy agents remain editable (vendor). [Salesforce: Builder migration](https://www.salesforce.com/agentforce/agent-builder/migration/). "Topics" were rebranded "subagents"; 100% execution consistency is a vendor-reported figure (third-party summary). [pulse.bot](https://www.pulse.bot/ai/news/refreshed-agentforce-guide-captures-a-year-of-innovation-and-script-success-5afae04b-ff23-402d-ae70-b7f7e1a808ea/)

### Inferences
- Two architectures exist. (a) "Rule is the program": Parlant guidelines, Agentforce instructions/Agent Script, Decagon AOPs, Sierra Journeys, Rasa flows, AgentCore NL policies. Drift between rule and enforcement is minimized by construction (or moved into the NL-to-compiled step). (b) "Rule is a requirement, enforcement is separate code": SDD tools and AK Studio. AK Studio's design is type (b), so its out-of-sync detection is necessary and is its main differentiator versus the CX platforms, but it must also explain why a separate rule layer is better than type (a) (answer: AK runs 8 frameworks whose enforcement mechanisms differ, so a framework-neutral rule registry linked to guardrails, tools, config and tests is the portable layer).
- AgentCore Policy's NL-to-Cedar with validation is the closest "plain language in, deterministic enforcement out" precedent, but it is scoped to tool-call authorization at a gateway, not general business logic, and offers no test coverage view in sources found.
- Platform testing is converging on simulation plus LLM-judged evals (Sierra, Agentforce Testing Center); AK already has a built-in test framework, so linking rules to AK tests and showing per-rule coverage is a credible, concrete differentiator.
- Business owners are the explicit audience of Sierra, Decagon, Agentforce and Copilot Studio; AK Studio competes there only if the rules UI hides code while still showing linked evidence.

## Q5. Is anyone doing "plain-language rule linked to enforcing code plus test coverage plus out-of-sync detection" in one place? How close is the nearest competitor?

### Takeaway
No product found combines all four (plain-language business rule as a first-class object, explicit links to enforcing code/config/tests, per-rule coverage, and an out-of-sync state with AI repair) in one UI. The nearest neighbours each cover two or three pieces: Kiro (requirements to property-based tests with traceability, developer-facing, IDE), the Tessl "spec-as-source" package (requirement to owned files and `[@test]` links, manifest, drift spot-check, no UI), Sierra Ghostwriter and Agentforce (natural-language rules plus auto-testing, but rule-as-program and platform-locked), and AgentCore Policy (natural language compiled to enforceable Cedar, tool-scope only). The combination is novel; each ingredient is crowded.

### Cited Findings
- Kiro: EARS requirements, properties extracted, generated tests, "traceable link between your requirements and the tests that validate them", failure triage across spec, implementation and test; IDE-only (primary docs). [Kiro docs: Correctness](https://kiro.dev/docs/specs/correctness/)
- Tessl spec-as-source: `targets:` file ownership, `[@test]` per requirement, link checks, manifest, semantic drift spot-check, CI sync (registry package). [spec-verify SKILL.md](https://tessl.io/registry/spec-driven-devlopment/spec-as-source/files/skills/spec-verify/SKILL.md); [spec-writer SKILL.md](https://tessl.io/registry/spec-driven-development/spec-as-source/3.1.1/files/skills/spec-writer/SKILL.md)
- Sierra Ghostwriter: natural-language guardrails, tests on every build, failure diagnosis and proposed fix (vendor). [Sierra: Ghostwriter](https://sierra.ai/product/ghostwriter)
- Agentforce: "always/before/never" instructions become deterministic logic; Testing Center with compliance-focused custom scoring evals (vendor). [Salesforce reliability guide](https://www.salesforce.com/eu/agentforce/resources/reliable-ai-agents-guide/); [TDX 2026 roundup](https://www.salesforce.com/blog/tdx-2026-roundup-agentforce-edition/)
- AgentCore Policy: natural language converted to Cedar and validated, enforced at the gateway (primary docs). [AgentCore: natural-language policies](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-natural-language.html)
- Parlant: per-turn record of which guideline matched and why (primary docs). [Parlant: Explainability](https://parlant.io/docs/advanced/explainability)
- Augment Intent: living spec updated as agents work and a Verifier checking against it (vendor). [Augment: Intent](https://augmentcode.com/blog/intent-a-workspace-for-agent-orchestration)
- Small drift tools (spec-gen, specsync, Pituitary) detect spec/code divergence via git mappings, stale checks or MCP context (open source / vendor). [spec-gen](https://gh.r-mj.com/clay-good/spec-gen); [specsync](https://docs.rs/specsync/); [Pituitary](https://dusk.network/news/pituitary)

### Inferences
- Novelty rating (judgment): "Build with AI" is low-to-moderate novelty as a concept (crowded) but moderate in form (local, open-source, framework-agnostic, canvas-highlighted AI changes with per-change accept/revert over a real code repo). "Business rules" is moderate-to-high novelty as a combined product surface, low novelty as individual mechanisms.
- Nearest competitor by mechanism: Tessl spec-as-source plus Kiro PBT. Nearest by audience (business owner writes rule, AI enforces and tests): Sierra Ghostwriter and Agentforce. AK Studio sits between them; the pitch should be "Kiro-style traceability for the business rules of agents, with the CX platforms' plain-language authoring, on an open runtime you own".
- Risk: Sierra and Salesforce already ship natural-language guardrails plus auto-testing to business users; if either adds a per-rule evidence view, the gap narrows for enterprise CX buyers. Kiro or Spec Kit could add standing "rules" with drift states cheaply since they already have steering files and analyze steps.
- Design implications worth carrying into the spec: (1) let "Fix with AI" choose whether to update the rule, the code or the test (Kiro precedent); (2) treat a rule with no linked test as a distinct, worse state than a failing test (spec-as-source precedent); (3) consider a CI check that fails on broken rule links, so `.akstudio/` rules are enforced outside the desktop app; (4) show which rule fired at runtime by linking rules to AK guardrail/trace events, as Parlant does for guidelines.

### Gaps
- Did not find independent (non-vendor) evaluations of any rule-authoring product's enforcement reliability.
- Could not confirm whether Sierra Agent Studio or Agentforce Testing Center expose any per-rule coverage or drift state; their docs were not fully retrieved.
- Did not search compliance/GRC tooling outside the agent space (e.g. policy-as-code platforms) for rule-to-evidence linking UIs; that adjacent category may hold closer UX analogues.
